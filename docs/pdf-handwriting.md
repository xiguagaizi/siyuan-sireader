# Independent PDF handwriting mode (MVP)

The PDF toolbar has a **手写笔记 / Handwriting** entry. It opens a separate touch-sized toolbar with Pen, Highlighter, whole-stroke Eraser, color, width, Undo/Redo, Finger writing, Fullscreen and Return. Every entry starts with Pen. Pen-up keeps the tool active without selecting the new ink or opening its editor. The original toolbar returns on exit.

This includes the MVP and tablet toolbar improvements. Pressure-dependent widths, smoothing, partial erasing, pen side-button shortcuts and an additional handwriting export workflow remain later work. Existing native PDF export operates on the same standard annotations; it is not a newly implemented export feature.

## Reuse and boundaries

- `src/handwriting/session.ts` supplies independent tool IDs, raw input routing, lifecycle and a whole-stroke hit test. `HandwritingToolbar.vue` owns the mode's controls; `EmbedPdfReader.vue` only connects them to the current document.
- Tools are registered through the snippet's `annotations.tools` configuration before page mounting. The entry also waits until the native page event providers have mounted; file/annotation readiness alone can precede those providers and lose an early first stroke. EmbedPDF 2.15.1's paint-layer effect does not register late-added tools for already mounted pages; relying on `addTool()` at mode entry can silently miss the first strokes.
- Drawing delegates sampling and preview to the actual native `ink.pointerHandler` / `inkHighlighter.pointerHandler`. EmbedPDF's page provider owns scale, intrinsic rotation, viewer rotation and natural page coordinates. There is no second viewer or independent canvas/page renderer.
- EmbedPDF 2.x normalizes pointer events without retaining `pointerType`, `pointerId` or pressure. A listener on this viewer's host captures the original event before native dispatch. Dedicated factories use that event synchronously for filtering; no synthetic events or global pointer handlers are installed.
- Native ink normally groups strokes for 800 ms. This mode commits the native preview at pen-up, then clears its draft through the native cancel method. It does not start the grouping timer. This gives each pen-down/up a separate standard INK annotation and allows synchronous final-stroke capture before teardown. Single-point dots receive a tiny second point.
- Pen and primary-button mouse draw/erase. By default one finger scrolls through `viewport.scrollTo`, using the fixed pointer-down coordinates and scroll origin just like native panMode; single-touch native scrolling is suppressed to prevent competing scroll updates, and single-finger panning resumes only after all fingers lift following a pinch; native zoom handles the two-finger Touch Events. Finger writing is an explicit per-reader toggle; adding a second finger cancels an unfinished finger stroke before pinch navigation.
- Automatic palm filtering runs before native navigation state changes. Real pen `pointerover`/`pointermove` events protect hover as well as pen-down, with a 650 ms grace interval. Nearby support contacts (initial separation below 80 CSS px) are quarantined as a group until all contacts lift, including when the pen never touches the page; their later motion cannot turn into a pinch. Single-finger panning waits 100 ms and requires 10 px of movement, allowing a second support contact or pen hover to cancel it before scrolling; a quick swipe of at least 30 px commits on release so it is not discarded by that intent window. Pointer cancellation does not revive an ongoing native Touch Events group.
- `src/handwriting/palmRejection.ts` also checks raw Pointer Event contact bounds and Touch Event ellipse axes (twice `radiusX`/`radiusY`, including oblique contacts). Clearly broad/elongated contacts are quarantined immediately. Borderline shapes need at least two observations spanning 40 ms, with no sample gap longer than 120 ms; pending evidence can briefly hold a pan for up to 80 ms. An ordinary measured shape clears unconfirmed evidence; a confirmed support group stays rejected until all contacts lift. Pointer IDs and Touch identifiers are tracked separately and reset at gesture end/mode exit. Missing, non-finite and default 1x1 sizes supply no shape evidence. The classifier uses conservative CSS-pixel thresholds, not physical millimeters or anatomical identification.
- The shape/lifetime policy is an independent TypeScript implementation informed by [iptsd's size/aspect and tracked-validity checks](https://github.com/linux-surface/iptsd/blob/9c7a55462f2bcf3268689e314dfcaaef884e16e6/src/contacts/validation/validator.hpp) and [Chromium's pre-admission hold and successive-sample classification](https://github.com/chromium/chromium/blob/091de37af62da9f9d901a9d2e5f10b109752731f/ui/events/ozone/evdev/touch_filter/neural_stylus_palm_detection_filter.cc). No upstream implementation, neural network, sensor heatmap pipeline or device-calibrated thresholds is imported. The public web input boundary remains unchanged.
- Deliberate, initially separated two-finger contacts still use EmbedPDF's real pinch handler. Once that native gesture has been admitted, it keeps ownership until touch-end; intercepting its partially rendered transform or compensating zoom after the fact can interrupt ink. Pen input resumes after that gesture ends. There is no permanent touch lock, synthetic touch replay, private zoom-method hook or replacement pinch engine.
- This is heuristic rejection, not hardware-level hand identification. A small/round support contact, widely separated support contacts with unavailable geometry and no hover, or imprecise browser contact data can still be misclassified. Shape changes after a genuine native pinch has already been admitted do not interrupt it; borderline shapes can be indistinguishable at initial touchstart. Actual iPad contact-size reports and thresholds need device validation. The interaction target is [Notability's documented palm detection with finger scrolling](https://support.gingerlabs.com/en-us/articles/16300204-writing-with-apple-pencil); the implementation is independent. [Excalidraw's pen/pinch separation](https://github.com/excalidraw/excalidraw/blob/701b901a0f1ba3d0b390d9cdf63d112e25abac4b/packages/excalidraw/components/App.tsx) and [tldraw's early input filtering fix](https://github.com/tldraw/tldraw/commit/7fffd343ae37fb97fc55436a3667a408f16ef0b3) are useful design references, not imported engines.
- Erasing checks the swept eraser segment against the ink's line segments, accounting for line width and zoom. It invokes native batch deletion without selection and only deletes INK annotations marked `custom.sireaderHandwriting = 1`. Existing PDF ink, highlights, comments and normal-mode annotations are preserved.
- The eraser shows a 20 px diameter screen-space ring and a short swept trail. Its hit radius uses the same screen size across zoom levels. Visual feedback is independent of annotation rendering and is removed on mode exit/disposal.
- Undo/Redo delegates to the native history plugin. Command counts group every deletion in one eraser gesture into one toolbar action. A fresh mode entry starts a new boundary; external history changes invalidate it so these buttons cannot undo unrelated original annotations. Native changes still use the existing save queue.
- The centered toolbar uses 36 px high aligned controls, wrapping into two rows on small phones. Color opens a 208 px panel with black/blue/red/yellow presets, saturation/value, hue, compact RGB/HEX inputs; width opens a keyboard-accessible checked menu. The handwriting entry registers its SVG in the actual dynamically loaded runtime, fixing the missing icon. Return, undo/redo and fullscreen use matching SVG strokes.
- Ordinary browsers with Fullscreen API support target the entire reader root, including the toolbar. Home Screen/standalone windows, missing APIs and denied requests use in-page expansion with a Restore layout action instead. A manual popover places the existing reader in the top layer without reparenting/reloading its custom PDF element; older browsers fall back to fixed positioning. Escape and mode exit restore the layout. This does not install or launch a PWA. Entry queues an early click until annotations and page handlers are ready rather than depending on the native command UI's cached disabled category state.
- The deployed host's desktop HTML omits the legacy `apple-mobile-web-app-status-bar-style=black-translucent` declaration. Status-bar space belongs to the host/system layout; the reader no longer adds its own safe-area padding. In-page expansion still follows visual-viewport dimensions. Fresh Home Screen installation and actual iPadOS layout need device verification.
- Mode exit restores the previous tool, interaction mode and annotation lock. Cancel discards a draft; capture loss and explicit exit/flush finalize visible ink. Source change, text-reflow switch and unmount detach mode listeners. A restricted PDF cannot silently enter a tool that the runtime refused to activate.

## Persistence

Handwriting uses the existing standard `AnnotationTransferItem` geometry and SiReader's normal per-book JSON record. The existing manual annotation commit queue and ID-based upsert/delete queue are unchanged. Entry waits for both annotation loading and the native page-handler effect batch, exit waits for commit and persistence, and unmount captures the last draft before the normal pending-save path runs.

The same record therefore participates in SiYuan's existing file sync. This does not introduce cross-device concurrent-edit merging or guarantee synchronization of two devices editing offline. Pen color/width and the finger toggle currently belong to the open reader instance.

Commands from the repository root:

```sh
pnpm install
pnpm test:run
pnpm build
# Install/provide Playwright separately, or set PLAYWRIGHT_MODULE to its entry.
# BROWSER_EXECUTABLE optionally selects an existing Chromium binary.
node scripts/check-pdf-handwriting-browser.mjs
```

- Thirty-six handwriting unit tests cover sweep hit testing, protection of original annotations, separate immediate strokes, pen retention, touch pan, two-finger takeover, palm contacts, finger-writing opt-in, cancellation, mode restoration, capture loss, mouse-button filtering, support motion without pen-down, hover filtering, group-lifetime quarantine, pointer cancellation, native pinch ownership, buffered pan cleanup, grouped eraser undo/redo, external history isolation, panning with stale viewport metrics and eraser feedback cleanup. Shape tests include single broad/elongated support, oblique Touch Event axes, repeated versus transient/stale borderline evidence, pending-pan cancellation, unavailable geometry, widely separated support, native pinch ownership across shape changes, finger-writing cancellation and recovery on the next contact.
- Browser coverage uses the actual Vue reader, bundled EmbedPDF 2.15.1/PDFium, CDP pen/touch input, mixed PDF page sizes and intrinsic rotation. It covers adjacent supporting fingers moving without pen contact; single broad, oblique elongated and persistent borderline contacts without any pen input; contact shrinkage; widely separated support with one elongated ellipse; hover rejecting widely separated support contacts; palm-first pen writing without view drift; continuous pen; highlighter width/opacity; finger-writing opt-in; no selected annotation; measured normal-finger pan without ink; real native pinch zoom; whole-stroke erasing; persisted undo/redo; compact color/width interaction; native fullscreen; Home Screen missing-API expansion; no reader-added safe-area padding even when an inset is exposed; no duplicate gap below a host header; drawing without remount during expansion; layout restoration; immediate exit; stored geometry after remount; rotation/zoom/page-coordinate projection; original ink preservation; and desktop/tablet/mobile toolbars.
- The browser fixture substitutes the SiYuan host storage boundary with in-memory records. It exercises the reader's commit/persistence bridge and reopen import. A separate installation smoke test against the existing SiYuan 3.8.9 service also passed real file-API autosave, undo deletion, redo restoration and remount with identical stroke ID/geometry. That test used an isolated temporary PDF, blocked document writes and removed its test record. The latest installation preserved all existing per-book record hashes across the program-directory replacement. Subsequent live validation ran while the service was active; an existing record and runtime shelf/focus state changed during that period, so it is not a quiescent whole-data snapshot and no active-session changes were rolled back. It does not verify multi-device sync. Existing storage tests exercise the storage layer separately.
- The existing real-browser text-reflow regression also passes: native scrolling/navigation, markup creation, source updates/deletes, repeated mode switches and legacy annotation backfill.
- Production build passes. Full Vitest result: 196 passed, 2 failed out of 198. The failures are the existing `copyMarkdown.test.ts` callback-arity expectation and `licenseFlow.test.ts` usage-report read expectation. Both reproduce on unmodified upstream commit `32d7ce779cf30f1274d3a9429e2d69394c81c241`; no unrelated behavior was changed to silence them.
- Two prerequisite build fixes retain behavior: resolve Foliate's existing short SHA to the identical complete commit, and correct `BookShelf.vue` to the tracked `Bookshelf.vue` import on case-sensitive Linux.

## Android tablet acceptance still required

1. Physical active-pen type/pressure reports, latency, fast small handwriting and dots.
2. Palm/finger support motion before the pen ever touches, native pen hover reporting, palm before/during/after pen contact, finger/pen alternation and deliberate pinch on the actual iPad Safari/PWA and Android WebView.
3. Long documents, dense ink, memory/heat, app backgrounding and close/reopen with real SiYuan file storage.
4. Two actual synced devices, including deletion propagation; do not assume concurrent offline edits are merged.
5. Installed light/dark/custom themes, compact color panel and fullscreen behavior in the device WebView.

Browser CDP input and screenshots do not substitute for these device checks.
